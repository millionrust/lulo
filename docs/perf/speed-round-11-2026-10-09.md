# Speed round 11 — 2026-10-09: the two SPEED-11/SPEED-12 leftovers

Branch `op/speed-11` on `integ` 078972db. Method as in rounds 7–10: a private
nested niri at 1920×1080 on the reference laptop, `iterate` profile, the
owner's live session running the whole time and never touched. "Before" and
"after" are the same laptop, back to back, `--repeat 5`. Raw reports are in
`speed-round-11-2026-10-09/`.

This round is mostly investigation: both items bottleneck on code outside
`crates/system-settings` and `shell/bins/rmac-app-switcher` (core `gpui`'s
window-refresh behaviour, and niri's own focus/action handling), confirmed
by reading the vendored `gpui` checkout and by correlating trace rows across
processes. The code change made is a safe, real cut of avoidable per-frame
work; it narrows the resize gap a little but does not close it.

## 1. System Settings live resize (SPEED-12)

### Finding: GPUI re-renders every cached view on every window refresh

`crates/system-settings/src/controller/views.rs` already draws the sidebar
and the detail pane as separate cached GPUI views (SPEED-02), so a frame
whose only dirty view is the pane should reuse the sidebar's last paint.
Reading the vendored `gpui` checkout's cache check
(`crates/gpui/src/view.rs`, `ViewElement::prepaint`) shows why that reuse
does not happen during a resize:

```rust
if let Some(mut element_state) = element_state
    && element_state.cache_key.bounds == bounds
    && element_state.cache_key.content_mask == content_mask
    && element_state.cache_key.text_style == text_style
    && !window.dirty_views.contains(&entity_id)
    && !window.refreshing
{
    // reuse the previous prepaint/paint range
}
```

`Window::bounds_changed` (`crates/gpui/src/window.rs`) calls `self.refresh()`
on every resize, and `window.refreshing` is true for the *whole* draw pass
while that is in effect — every cached view's reuse check fails, regardless
of whether its own bounds changed. The sidebar has a fixed column width and
never resizes in this test (only the window's overall width does), so it
still fully re-renders, re-lays-out and re-prepaints every frame. This is a
`gpui` core behaviour (the git-pinned `zed-industries/zed` dependency, not
the vendored `shell/compat/gpui_linux` backend), so it cannot be fixed from
this crate without vendoring `gpui` itself (a new ADR, owner-approved, per
the 0013 precedent) — matching round 10's own conclusion.

The vendored resize path from `op/speed-10` (swapchain reserved at the
largest output and cropped, not rebuilt per configure) **is** in effect for
Settings: `swapchain_kept` is 91–94 of 92–96 configures in every run below,
with exactly one rebuild (the resize-end shrink).

### Finding: both the sidebar and the pane spike together, correlated with size

Adding `rmac_ui::trace_mark` timestamps already in the tree
(`settings_sidebar_render`, `settings_pane_render`) and measuring the gap
between them (sidebar's own `render()` + `layout_as_root` + `prepaint_at`)
across one full edge-drag trace (`--keep`, 80 frames with both marks):

- sidebar cost: p50 5.4 ms, p95 25.3 ms, max 32.8 ms
- pane cost: p50 5.6 ms, p95 20.2 ms, max 30.2 ms

Both subtrees are comparably cheap on the median frame (together under the
16.7 ms budget with room to spare) but spike 4–6× on some frames, and the
spike size tracks the drag: costs rise through the first (growing) drag and
fall through the second (shrinking) one, not randomly. Neither subtree's own
content changes with width (the sidebar is a fixed column; the detail
column's content has a fixed max-width and is centred), so this is read as
further confirmation of the forced-refresh cost scaling with the window's
own size inside `gpui`'s layout pass, not something `cargo clippy`-visible
in this crate. `perf record` could not confirm the exact internal mechanism
further: the laptop's `perf_event_paranoid` is 4, which refuses it without
`sudo` (not available here, and not permitted).

### Change made

`crates/system-settings/src/controller/chrome.rs`'s sidebar render always
called `search_matches()` (ranks every category against the search query)
and formatted a fresh `"cat-{si}-{ci}"` string per row, on every single
render — including every one of these forced resize re-renders, even when
there is no search query at all (the common case) and the row ids never
change. Both are now skipped/avoided when not searching: `search_matches`
is computed only while `searching`, and row ids are a `(&'static str,
usize)` composite `ElementId`, not a `format!` allocation.

### What is still left

Getting to 95 % needs one of:
- Vendoring `gpui` (ADR + owner approval) to stop `Window::refresh()` from
  invalidating every cached view's reuse check, only the ones whose own
  bounds actually changed.
- Or a cheaper Settings pane specifically while an interactive resize is in
  progress — risky for the Beta quality bar (a visibly different "resize
  mode" is its own kind of unpolished), not attempted here.

## 2. ⌘Tab quick tap (SPEED-11)

### Finding: the ~100 ms is two sequential, niri-side round trips

Running `cmd-tab` with `--keep` and reading the switcher service's own trace
alongside the target apps' traces (same wall clock via each trace's own
`monotonic_origin`), one full quick-tap cycle breaks down as:

1. **Spawn `app-switcher next`**: ~14 ms (niri forking the bound command).
2. **Switcher surface gets the keyboard** (`switcher_reshown` → `focus_in`):
   ~23 ms. This is niri handing the exclusive-keyboard layer-shell surface
   its `wl_keyboard` focus — the *only* way the switcher can read whether ⌘
   is still down (GPUI's `window.modifiers()` only updates once a surface
   has the keyboard; there is no seat-wide "is a modifier held" query
   available without it).
3. **Grace timer**: ~4–5 ms (`RELEASE_GRACE`, already tuned down from 80 ms
   in earlier rounds; this covers niri dispatching the keyboard-enter and
   the modifiers-changed event in the same flush, not a gap worth cutting
   further without risking the quick-tap/hold misdetection that grace
   exists to prevent).
4. **`commit()` → `activate()` → niri's `FocusWindow` action, round trip**:
   `switcher_commit` to `switcher_activated` is **~57 ms** in the traces —
   by far the largest single piece. `rmac_compositor_niri::execute_at`
   itself adds no artificial delay for a single-window target (the
   between-actions `Timer::after(50ms)` in `runtime.rs` only applies when a
   sequence has more than one action, e.g. a floating-frame move); this is
   genuinely niri processing (and, under this test's nested Sway/software
   compositing, possibly also presenting) the focus change.
5. Target app's own configure → redraw → present: a few ms (Calculator and
   Clock are both small).

14 + 23 + 5 + 57 ≈ 99 ms, matching the measured ~103–105 ms closely.

### Why no code change here

Steps 2 and 4 are both niri round trips, not rmac code: step 2 is
unavoidable without changing *when* we ask for that confirmation (see
below), and step 4 has no added delay on our side to remove. Two ways to
cut this were considered and not taken:

- **Split `next`/`previous` into a tiny, GPUI-free binary** to cut the 14 ms
  spawn. Checked with `ldd`: the current binary already has almost no
  shared-library dependencies (`libc`, `libm`, `libgcc_s`, `libxkbcommon`
  only — Vulkan/font drivers load via `dlopen` at runtime, not `DT_NEEDED`),
  so a split would save at most a couple of ms of ELF-loading overhead, for
  the cost of a second installed binary touching packaging's binary
  contract (`scripts/linux/native_package_contract.py` and friends, and
  `packaging/rmac-session/shell.kdl`) — not a good trade for the size of
  the win.
- **Switch optimistically** (fire the `FocusWindow` action for the first
  Tab's target immediately, in parallel with opening the switcher surface,
  instead of waiting for the surface to confirm ⌘ is still down): this would
  take steps 2–3 off the critical path, since step 4 already runs
  independently once dispatched. It is the only lever left that could
  plausibly reach the 50 ms target. It was not implemented: on ⌘. / Escape
  the switch would need to be *reverted* (re-focus whatever had focus
  before), which this codebase cannot validate without live interactive
  testing on the owner's session (forbidden), and a wrong focus-handoff
  edge case (double-activation, a visible flicker) would be a worse
  regression than the current, honest "quick tap FAIL" — left for a round
  that can test it interactively.

## Harness changes

- `scripts/behavior/speed_interactions.py`: `resize-drag-long` and
  `resize-drag-edge` now score `pass` against a dedicated
  `RESIZE_FRAME_SHARE_TARGET` (95 %), not the generic 99 % scrolling target
  they inherited from `frames_summary`'s default — the two have different,
  intentional goals and should not share one pass/fail line. `cmd-tab`'s
  `pass` now checks `CMD_TAB_TAP_TARGET_MS` (50 ms, matching the held path's
  already-met target) instead of the old 100 ms placeholder.
