# Speed round 10 — 2026-10-07: resizing without rebuilding, the held ⌘Tab, Settings' extra frame

Branch `op/speed-10` on `integ` 44870401 (speed-9 merged). The method is the
same as rounds 7–9: a private nested niri at 1920×1080 on the reference
laptop. The owner's live session was running on the laptop the whole time,
and nothing here touched it. Every sweep held the shared build lock, so no
build could run during a measurement. "Before" is `integ` and "after" is this
branch, both built with the `iterate` profile on the same laptop. Settings is
also measured with a release build. The raw reports are in
`speed-round-10-2026-10-07/`.

## Harness

- New `resize-drag-edge`: the drag from Settings' own right edge, in its
  client-side resize border. The client starts niri's resize, which is how
  people resize a window. `resize-drag-long` (niri's Mod + right-drag)
  stays.
- Resize scenarios now report `swapchain_rebuilds`, `swapchain_kept`, and
  the p95 and maximum time from a configure to the frame that answers it.
- New trace rows: `renderer_kept`, `renderer_shrunk`, `theme_refresh`, and
  `settings_render`, `settings_sidebar_render`, `settings_pane_render`,
  `settings_notified` and `settings_pane_notified` (through
  `rmac_ui::trace_mark`, which wraps `gpui_linux::trace_mark`).

## Changes

1. **No swapchain rebuild per resize configure** (SPEED-12, `gpui_linux`
   and `gpui_wgpu`).
   - While an interactive resize runs, the swapchain is allocated at the
     size of the largest output, rounded up to 64 px, and cropped to the
     window with `wp_viewport.set_source`.
   - The scene is drawn 1:1 into the top-left corner (the projection uses
     the image size), so nothing is stretched.
   - For a resize the client starts (an edge drag), the swapchain grows when
     the drag starts. At that point niri is not yet waiting on a configure
     answer, so the rebuild does not block.
   - 500 ms after the resize ends, it shrinks back to the window with one
     rebuild, again while niri is not waiting.
   - Every other configure in the drag draws into the swapchain it already
     has.
2. **⌘Tab held: the switcher's swapchain is reserved at panel size**
   (SPEED-11).
   - When the switcher surface opens at 1 × 1, its swapchain is allocated
     for the widest panel the display can show (`reserve_window_drawable`),
     and the viewport shows only the 1 × 1 corner.
   - Revealing the panel then changes only the crop, in the same frame.
   - Shrinking back is free too, so revealed switchers are now kept and
     re-shown like quick-tap ones.
3. **Settings' frame after activation was a theme refresh** (SPEED-02).
   - The new rows show no `settings_notified` before that frame, then a full
     render of the root, sidebar and pane: a `theme_refresh`.
   - Every app started with the default tokens and resolved the user's
     stored preferences (accent, highlight, wallpaper tint) asynchronously.
     About 200 ms in they replaced the defaults, and `refresh_windows`
     re-rendered every window. niri then drew that frame when it activated
     the window.
   - The theme is now seeded from the stored preferences before the first
     frame (two small file reads). The host's own appearance still arrives
     from the portal asynchronously. That is a real change only when the
     host's light/dark setting differs, and then the first frame already
     shows the user's colours.

## What is left

- **Resize frames.** No configure waits on the swapchain any more. GPUI's
  render (layout, prepaint and paint of the whole Settings window) is
  9 ms p50 but 25–36 ms p95 in the iterate build, which keeps the drag at
  70–76 %. Every resize is a GPUI refresh: upstream `Window::bounds_changed`
  calls `refresh()`, so even cached views whose size did not change are
  rendered again. Getting to 95 % means not refreshing on resize in GPUI
  (a vendored or patched `gpui`, since it comes from the zed git
  dependency), or making the Settings pane cheaper to lay out.
- **niri's Mod + right-drag.** niri starts this resize itself, so the client
  learns of it only from the first resize configure. Growing the swapchain
  then blocks once, for 355–546 ms. niri could send the resizing state
  before the first size change; otherwise the next step is to grow on
  the first configure that carries the resizing state with the old size.
