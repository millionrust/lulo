# ADR 0017 — Mac shortcuts in every app use keyd, driven by rmac's own niri focus follower

- **Status:** accepted 2026-09-23; privilege model revised 2026-09-24 (security finding SR-13,
  see "Revision: keyd's group is root" below).
- **Scope:** `crates/rmac-keyboard` (generator, the `rmac-mac-keyboard` helper and follower),
  `rmac-mac-keyboard.service`, `packaging/rmac-session/{debian,polkit}`, and the PC Keyboard group
  in System Settings › Keyboard (`design-lab/settings.html`, Keyboard frame).

## The question

rmac's own apps and niri read ⌘ as Super: ⌘C copies in Files, ⌘Space opens Spotlight. Apps made
for PC keyboards (Firefox, GTK and Qt apps, Electron, VS Code, terminal emulators) expect Control.
So on a Mac-trained hand ⌘C does nothing in Firefox, and in a PC terminal Control-C copies
instead of interrupting.

On the Mac, ⌘C/⌘V/⌘X/⌘Z/⌘A/⌘S/⌘W/⌘Q/⌘T/⌘F work the same in every app. ⌘←/⌘→ go to the start or
end of the line. ⌥←/⌥→ move by word. Terminal copies with ⌘C and keeps ⌃C for SIGINT. On a PC
keyboard, ⌘ should also sit next to the space bar, where the Mac has it (PC keyboards put Alt
there). What is the cleanest way to get all of this on Ubuntu 26.04 with niri, for every app?

## Options

| | keyd + keyd-application-mapper | xremap | niri only | keyd + rmac follower (chosen) |
|---|---|---|---|---|
| Rewrites keys for | every client, the TTY and the greeter (evdev → uinput) | every client (evdev → uinput) | — | every client (evdev → uinput) |
| Knows the focused app on niri | through wlr-foreign-toplevel (Python) | yes, `--features niri` | yes | yes, through niri's IPC event stream, which rmac already parses (`rmac-compositor-niri`) |
| In the Ubuntu 26.04 archive | `keyd` 2.5.0-5 (universe); mapper is a separate Python package | no; rmac would have to ship a static binary | — | `keyd` 2.5.0-5 (universe) |
| Privilege model | root daemon; the mapper needs the user in group `keyd` | a user process that reads every keyboard, so the user joins `input`, which amounts to a keylogger for any user process | none | root daemon; the follower asks a root-installed relay for one of three profiles, and no session joins `keyd` |
| Per-app behaviour | a user-written `app.conf` | a user-written YAML file | — | generated by rmac and unit-tested |

**niri alone cannot do it.** niri binds keys to its own actions (and `spawn`). It cannot turn a
chord into another chord and deliver it to the focused client, so ⌘C can never reach Firefox as
Control-C. It stays the owner of ⌘Space, ⌘Tab, ⇧⌘3/4/5 and ⌃⌘Q.

**xremap** is the nearest competitor. It is Rust, it knows niri, and it is flexible. It is not in
the archive, though, and running it as the user means putting that user in `input`, so every
process they run could read the raw keyboard. keyd keeps raw input inside one root daemon. Its
socket for rebinding is root-equivalent (see the revision below), so rmac keeps sessions away from
it too.

**keyd** is packaged. It already runs before the display server, so the same layout also works at
the greeter and on the TTY. It has first-class modifier layers (`[cmd:M]`: Super for anything not
bound), composite layers (`[cmd+control]`) and an IPC `bind` command that changes bindings at run
time without a restart. Upstream's `keyd-application-mapper` is a Python poller. On niri it has to
use wlr-foreign-toplevel, and it reads its rules from a hand-written file. rmac already follows
niri's focus in Rust, so a small follower in the same crate replaces the mapper, and the rules
become generated and tested data.

## Decision

1. **Opt-in, off by default.** System Settings › Keyboard › PC Keyboard › *Use Mac shortcuts in
   all apps*. Turning it on runs `pkexec /usr/libexec/rmac/rmac-mac-keyboard apply …`, whose
   arguments are enumerated flags only (`helper.rs`). The polkit action is
   `org.rmac.mac-keyboard.apply`, `auth_admin_keep`. The helper:
   - writes `/etc/keyd/rmac.conf` (0644);
   - removes the requesting user (`PKEXEC_UID`) from group `keyd` if a development build put
     them there;
   - runs `systemctl enable` and `systemctl restart keyd.service`;
   - runs `systemctl enable --now rmac-mac-keyboard-relay.socket`;
   - removes the XKB copies of the swap and Caps Lock options from localed (below).

   It refuses to run when another `/etc/keyd/*.conf` exists, so a user's own keyd configuration is
   never overridden. Turning it off disables the relay socket, deletes the file, removes a
   leftover `keyd` membership, and disables keyd if nothing else uses it.
2. **The installed file does nothing by itself.** ⌘ keys activate `[cmd:M]` and ⌥ keys activate
   `[opt:A]`, and both are empty, so as installed rmac apps and niri see exactly what they saw
   without keyd. The first line records the layout
   (`# rmac-mac-keyboard 1 swap=on caps=control option-characters=off`). Settings reads its state
   back from that line, and the package's `postinst` uses it to regenerate the file on upgrade.
   There is no second store.
3. **The follower fills the layers per focused app.** `rmac-mac-keyboard follow` runs as the user
   unit `rmac-mac-keyboard.service` (`ConditionPathExists=/etc/keyd/rmac.conf`). It watches niri's
   event stream. On each focus change it writes one profile name (`native`, `pc-app` or
   `terminal`) to `/run/rmac-mac-keyboard.socket`. The relay behind that socket runs one
   `keyd.rvaiya bind reset …` command with that profile's generated bindings (Debian renames
   upstream's `keyd` binary; see Debian bug #1098982). There are three profiles:
   - **Native** (`org.rmac.*`, layer-shell surfaces, no window): `reset` only. ⌘ stays Super.
   - **PC app** (every other app ID): ⌘A B C F G I K L N O P Q R S T U V W X Z 0 = − → Control
     with the same key. ⌘[ / ⌘] → Alt-←/→. ⌘←/→ → Home/End. ⌘↑/↓ → Control-Home/End. ⌥←/→/↑/↓/⌫/⌦ →
     Control with the same key. Shift passes through, so ⇧⌘Z sends Control-Shift-Z.
   - **Terminal** (20 known PC terminal app IDs): ⌘C V T N W Q F A → Control-Shift with the same
     key. ⌥←/→ → Esc-b / Esc-f and ⌥⌫ → Esc-Delete, which are the Mac Terminal's defaults. ⌃C is
     never touched.

   niri's own ⌘ bindings are never translated. Space, Tab, grave, 3/4/5, H and M are unbound in
   every profile (a unit test enforces this). Every translated key is also bound in
   `[cmd+control]` to itself, so ⌃⌘Q still locks and ⌃⌘F still goes full screen while Firefox
   has focus.
4. **The physical layout is one setting with two backends.**

   | Choice | Mac shortcuts off: localed XKB | Mac shortcuts on: keyd |
   |---|---|---|
   | ⌘ next to the space bar | `altwin:swap_alt_win`, or `altwin:swap_lalt_lwin` when a Mac variant makes Right Alt the ⌥-character key | Alt keys → `layer(cmd)`, Windows keys → `layer(opt)` |
   | Caps Lock → Control / Option / Command / Escape / No Action | `ctrl:nocaps` / `lv3:caps_switch` / `caps:super` / `caps:escape` / `caps:none` | `layer(control)` / `layer(opt)` / `layer(cmd)` / `esc` / `noop` |
   | ⌥ types special characters | the layout's Mac variant (from xkeyboard-config `base.xml`: `us(mac)`, `gb(mac)`, `de(mac)`, … 31 entries) | same variant, and `[opt:G]`: AltGr reaches the Mac variant's third level, while ⌥-arrows still send Alt for rmac apps |

   With Mac shortcuts on, keyd does the swap before XKB sees the keys, so the XKB swap and Caps
   Lock options are removed. Otherwise every key would be swapped twice. Options rmac does not
   own, such as `grp:*` and `compose:*`, are always kept.

## Consequences

- Turning the feature on needs one authentication prompt and works at once: no group membership
  is involved, so no new login is needed. If the relay is not listening, Settings says so and ⌘
  keeps working as Super everywhere (the installed file passes it through).
- Any local process can pick one of the three profiles through the relay. That is no more than
  focusing a different window does, and it cannot bind anything else.
- keyd applies `bind` to the most recently used keyboard. With two keyboards, the other one keeps
  the previous app's profile until it is used and focus changes again. This is an upstream limit;
  it is recorded here and not worked around.
- Focus changes land a few milliseconds after niri reports them, so a chord pressed in that window
  uses the previous app's profile.
- With ⌥ characters on, ⌥⌘ letter shortcuts in rmac apps see AltGr, not Alt. That is the price of
  typing Mac characters. It is off by default.
- Custom ⌘-letter shortcuts a user adds in niri are translated in PC apps, like any other ⌘ chord.
- Removing `rmac-session` deletes `/etc/keyd/rmac.conf` (`postrm`) and disables keyd if nothing
  else configures it.
- Not done: per-app overrides in the UI, ⌘1…9 tab switching (which would collide with ⇧⌘3/4/5),
  ⌘⌫ (which means "move to Bin" in file managers), and Globe/fn remapping (PC keyboards have no
  Globe key).

## Revision: keyd's group is root (2026-09-24, SR-13)

The first version of this decision added the user to group `keyd` so the follower could call
`keyd bind`. Reading keyd 2.5.0's source (`src/ipc.c`, `src/daemon.c`, `src/config.c`,
`src/keyboard.c`) shows what that group grants:

- The daemon runs as root. `ipc_create_server()` only changes its *group* to `keyd` and makes
  `/var/run/keyd.socket` mode 0660, so every member of `keyd` can connect. `handle_client()` does
  no peer-credential check of any kind.
- `IPC_BIND` passes the client's text to `kbd_eval()` → `config_add_entry()`, which accepts any
  binding the configuration file accepts, including `command(…)`. On the next key press
  `execute_command()` forks and runs `/bin/sh -c …` as the daemon, so as root.
- `IPC_INPUT` and `IPC_MACRO` type arbitrary text and key sequences into whatever surface or VT
  has focus, around Wayland's client isolation.
- `IPC_RELOAD` reloads the configuration, and `IPC_LAYER_LISTEN` streams layer changes.

Debian's 2.5.0-5 patches (the version in Ubuntu 26.04) do not change any of this. So membership
of `keyd` gives every process of that user root and global keystroke injection. It was never
removed when the feature was turned off.

**Revised design.** No session is ever added to `keyd`, and the helper removes a membership that
earlier development builds added. Sessions reach keyd only through the relay:

- `rmac-mac-keyboard-relay.socket` (system unit, `/run/rmac-mac-keyboard.socket`, mode 0666,
  `Accept=yes`) is enabled by the helper only while the feature is on, and disabled when it is
  turned off or the package is removed.
- `rmac-mac-keyboard-relay@.service` runs `rmac-mac-keyboard relay` once per connection, as a
  `DynamicUser` whose only extra group is `keyd`, with no capabilities, `NoNewPrivileges`, a
  read-only system, no network and AF_UNIX only. It reads at most 32 bytes. The request must be
  exactly `native`, `pc-app` or `terminal` followed by a newline (`parse_relay_request`). It
  then sends that profile's generated `bind` arguments, which a unit test proves never contain
  `command(`. It answers `ok` or `error`.

The relay does hold the root-equivalent group, but its whole input is one of three fixed
words, so what a session can do through it is exactly what focusing a window does.
