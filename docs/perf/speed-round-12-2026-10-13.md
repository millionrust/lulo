# Speed round 12 (2026-10-13): GPUI core vendored, live resize, optimistic ⌘Tab

Branch `op/speed-12`, built on `integ` plus `op/speed-11`. The method is the
same as in rounds 7–11:

- a private nested niri at 1920×1080 on the reference laptop (i5-5300U);
- the `iterate` profile, `--repeat 5`;
- the owner's live session was never touched.

This round, "before" and "after" are the **same binaries**. Two opt-out
switches turn each change off:

- `RMAC_GPUI_RESIZE_REFRESH=1` brings back upstream GPUI's full refresh on
  every resize (ADR 0026).
- `RMAC_APP_SWITCHER_OPTIMISTIC=0` turns the optimistic ⌘Tab switch off.

The before and after runs were interleaved three times, one right after the
other. Nothing else was running on the laptop. Its 1-minute load stayed
between 2.6 and 6.0, almost all of it from the measured nested session
itself. The raw reports are in `speed-round-12-2026-10-13/`
(`final-<item>-<before|after>-<n>.json`, plus `final-cancel.json`).

## 1. System Settings live resize (SPEED-12)

### What changed

Round 11 found that `Window::bounds_changed` refreshes the whole window on
every configure. That makes every cached view render, lay out and paint
again on every resize frame. Fixing it took four changes:

1. **Vendor GPUI core** (`shell/compat/gpui`, ADR 0026). `bounds_changed` no
   longer refreshes for a new size or position. A new scale factor or a
   new display still refreshes.
2. **Compare the clip only where the view draws.** The cache key compared
   the whole content mask. With no clipping parent, that mask is the whole
   window, so it changed on every resize even after the refresh was gone.
   The key now compares the mask intersected with the view's own bounds.
3. **Track geometry reads per part.** A cached view records which parts of
   the window's geometry it read (viewport size, bounds, maximized,
   full-screen, decorations) and their values. It renders again only when
   one of those values changes. Settings' sidebar now takes its
   master/detail split from the root view instead of reading the window's
   width.
4. **Stop the text input dirtying its view on every paint.**
   `RMAC_GPUI_CACHE_TRACE=1`, which prints why each cached view missed its
   cache, showed the sidebar still re-rendering on 73 of 84 frames, marked
   dirty each time. The vendored gpui-component input element called
   `cx.notify()` from every paint. That dirtied the search field's
   `InputState`, and with it the sidebar around it, for the next frame. The
   input now notifies only when its bounds, caret, selection, scroll size
   or scroll offset changed.

After the fourth change, the sidebar rendered on 13 of 104 frames in one
edge drag. The detail pane still renders on every frame, because its width
is what changes.

|---|---|---|---|

| Edge drag, frame p50 / p95 (ms) | — | 8.0 / 24.0, 7.7 / 31.5, 11.3 / 26.4 | 5.8 / 15.0, 3.8 / 18.7, 6.4 / 15.1 |

- **Edge drag.** This is how people resize a window, from its right edge.
  It now meets the 95 % target in two of the three runs (median 96.4 %).
  Render time per frame is less than half what it was.
- **Mod-drag.** This is niri's Mod + right-drag. It improved by about 20

  23 to 45 frames, so one or two slow frames move the share by 2 to 4
  points. Its slow frames are the first frame after a configure. The pane,

- **Worst frames.** Every run still has one frame of 40 to 72 ms, at the

## 2. ⌘Tab (SPEED-11)

### What changed

The switcher service now focuses the session's first choice optimistically.
The first version did this as soon as the command arrived. Measured with new
frame-capture checks, it made things worse:

- **The target app blinked.** When niri applied the focus before the
  switcher's exclusive keyboard grab, the app was drawn active, then
  inactive when the switcher took the keyboard, then active again
  (`focus_in` → `focus_out` → `focus_in` in the app's own trace).
- **The panel flashed on a quick tap.** niri's focus change delayed the
  switcher's keyboard grab past the reveal delay, so the panel showed in
  3 of 5 quick taps.

Final design (`shell/bins/rmac-app-switcher`):

- **When it starts.** The optimistic `FocusWindow` goes out when the switcher
  surface **gets the keyboard**. niri moves its focus, but it cannot hand
  the app the keyboard while the switcher holds it. So the app is drawn
  active once, when the switcher closes.
- **Commit to the optimistic app.** A commit to that app sends nothing more.
  If niri has not yet answered the optimistic request, the switcher waits
  for the answer before it closes. That way the keyboard never goes back to
  the app that was frontmost on the way.
- **Commit to another app.** That app is activated after the optimistic
  request has landed, so the two can never apply out of order.
- **Cancel.** Esc, ⌘. or another surface taking the keyboard focuses the
  original window again. The surface stays mapped, still holding the
  keyboard, until niri has answered. The app switched to ahead never gets
  the keyboard.
- **Hidden apps** (a restore moves windows between workspaces) still wait
  for the user's choice, as before.

### New behaviour checks (`scripts/behavior/speed_interactions.py`)

- **`cmd-tab` and `cmd-tab-hold`** follow niri's focus changes
  (`niri msg -j event-stream`, read on a thread) and the target app's own
  `focus_in` rows. They fail when anything but the target comes forward,
  when the target gains the keyboard more than once, or, for a quick tap,
  when the panel showed. A quick tap is now scored on the target's frame
  after its **last** keyboard enter, so an early active frame that is then
  taken back does not count as a switch.
- **`cmd-tab-cancel-escape` and `cmd-tab-cancel-period`** hold ⌘Tab, cancel
  while ⌘ is held, let go, and check two things: the original app ends up
  frontmost, and the app switched to ahead never got the keyboard.
- **Rounds the harness skips.** The harness presses Super only after niri's
  Alt-Tab bind has fired. When the switcher gets the keyboard first, it sees
  a quick tap, and that round is skipped and reported as `raced`. The
  quick-tap and held checks use the same press sequence they used before.

### Results

| Interaction | Target | Before (3 runs) | After (3 runs) |
|---|---|---|---|
| Quick tap, stroke → target's settled active frame (ms) | ≤ 50 | 102.4 / 103.0 / 100.7 | 99.0 / 98.5 / 100.3 |
| Held, stroke → panel's first full-size frame (ms) | ≤ 50 | 42.7 / 43.9 / 42.8 | 52.1 / 43.3 / 43.6 |
| Held, release ⌘ → chosen app's frame (ms) | — | 56.3 / 56.7 / 56.5 | **28.9 / 28.6 / 26.4** |
| Flicker (blink, detour or panel on a quick tap) | none | none | none |
| Cancel restores the original app, no blink | yes | — | yes (Esc and ⌘.) |

- **Held path.** It is twice as fast on release: the chosen app already has
  niri's focus, so closing the switcher is all that is left.
- **Reveal.** Unchanged, except for one 52 ms run.
- **First tap after launch.** In both modes, the first quick tap after the
  service starts takes over a second and shows the panel. That is the
  surface's first map, already the case in round 11, and it is not counted
  in the medians.

### Why the quick tap is still about 100 ms

One quick tap, traced across the service and both apps on one clock, after
the change. Times are from the moment the service maps the kept surface
again:

| Step | At (ms) |
|---|---|
| `app-switcher next` spawned and the command received (before the map) | about −14 |
| Switcher surface gets the keyboard; optimistic `FocusWindow` sent | 24 |
| Release grace over, commit | 29–31 |
| niri answers the `FocusWindow` request | 44–46 |
| Surface unmapped | 44–46 |
| niri hands the keyboard to the target | 84 |
| Target's active frame presented | 86 |

So 14 + 24 + 5 + 15 + 40 ≈ 100 ms. Before the change, the last two steps
were niri's `FocusWindow` round trip after the commit, about 57 ms. Now they
are its answer to a request already in flight (about 15 ms) plus handing the
keyboard back after the unmap (about 40 ms). The total barely moved.

Every remaining step is niri's. Under the nested session's software
compositing, niri applies a change only when it next redraws: the outer
headless Sway renders with pixman. On the laptop's own GPU session both
steps should be much shorter, but this harness cannot measure that.

- **What can still be cut on rmac's side:** only the release grace (4 ms)
  and the wait for niri's answer. Closing without that wait would let the
  keyboard return to the original app for a moment whenever niri applied
  the unmap first, which is the blink this round set out to avoid.
- **Keeping niri's action socket open:** this was looked at and not done.
  niri answers one request per connection, and connecting to a local socket
  costs microseconds, not the 15 ms seen here.

## 3. Settings first-frame "wallpaper inset" failure (speed-11 CI)

`op/speed-11`'s runtime run 37885753913 failed `Settings first-frame has no
wallpaper inset` (edge (47, 47, 47) against content (31, 31, 41)). The same
job, re-run on the same commit, passed with edge (32, 33, 45) and content
(29, 29, 40). It also passed on `op/speed-12`'s first CI run (37892048856)
and on two other branches the same morning.

The check takes its screenshot while the window is still at its pre-fit
geometry (279, 0, 723, 832). A capture that lands before Settings' first
frame reads a pixel that has not been drawn yet. This is a timing flake,
not a regression from the sidebar change.

Two other runtime checks failed on this branch's run:
- `desktop-paint` (three login captures);
- `menu-dismiss` (Escape focus; `notify-send` is missing on the runner).

Both fail the same way on every other recent branch checked (`agent/gaps3`,
`agent/winshare6`, `agent/speed11`), so neither comes from this branch.
